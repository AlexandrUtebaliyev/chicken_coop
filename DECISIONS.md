# Решения, принятые без подтверждения

Коротко — что решил сам и почему, раз задача требовала работать автономно (см. CLAUDE.md).

- **Статус марки, если ячейка «Статус» пуста**: отгружено ≥ заказа → «Отгружено»; иначе готово ≥ заказа → «Готово»; иначе готово > 0 → «Готово частично»; иначе покрашено > 0 → «Покраска»; иначе изготовлено > 0 → «Изготовление»; иначе «Не начато». Формула подобрана и проверена по реальным строкам снимка (`Б-6`, `Б-10`, `МП-1`, `ПР1-9` и др.) — во всех случаях совпала с готовым статусом из таблицы.
- **Число вида `"1,968"` (запятая без точки)**: если все группы после первой запятой ровно по 3 цифры — это тысячи (`1968`), иначе запятая — десятичный разделитель (`12,5` → `12.5`). Правило из PROMPT.md было неполным для этого случая, выбрал вариант, который даёт верные эталонные суммы.
- **Наименование группы при равной частоте первых слов** (пример из PROMPT.md: «Колонна / Стойка» для группы СТ): беру все слова с максимальной частотой, сортирую по алфавиту и соединяю через « / ». Если слово одно — показываю его одно, без слэша.
- **Сортировка «Марки»**: «по готовности» — по возрастанию (сначала наименее готовые, это то, что обычно нужно увидеть в первую очередь в цехе); «по весу» — по убыванию (сначала самые тяжёлые). В PROMPT.md направление не указано.
- **Экран птичника по умолчанию**: переключатель «Только недостающие / Все» открывается в режиме «Только недостающие» — это чаще нужная информация на складе.
- **Статус птичника «Собирается»**: отдельного цвета в палитре PROMPT.md для него нет, использовал синий (`--status-partial`), как у статуса марки «Готово частично» — тот же смысл «в процессе».
- **Иконка приложения**: логотипа компании не было, сделал простой домик (ассоциация с «птичником») в фирменном синем цвете интерфейса; сгенерирован PNG вручную через Node (`zlib` + ручная упаковка PNG-чанков), без внешних библиотек и сети.
- **Journal (История) недоступна офлайн без кэша**: не считаю это фатальной ошибкой всего приложения — карточка марки открывается, просто блок истории показывает «История недоступна», т.к. основная функция (готовность) не зависит от журнала.
- **Pull-to-refresh**: порог срабатывания — свайп вниз на 90px от верха списка, без отдельного визуального индикатора (используется тот же крутящийся значок «Обновить» в шапке, что и при нажатии кнопки).

## Правки после первой сдачи

- **Баг «не работают прогресс-бары» на «Птичниках» и в карточке марки**: `.bar-fill` — это `<span>` (строчный элемент), а CSS `width`/`height` на обычном строчном элементе браузер игнорирует вообще, даже если значения заданы инлайново. Поэтому заливка полосок была невидимой — виден был только пустой трек. На «Марках» бары работали, потому что там другая реализация (`.stack-bar > span` с `position: absolute`, что блочит элемент автоматически). Исправлено добавлением `display: block` в `.house-stage-row .bar-fill` и `.stage-detail-row .bar-fill` (styles.css).
- **«Состав марки»**: добавлен как отдельный, третий источник данных — Google-таблица `1N9trmeZmpaDhrSThcVps2aFEKQ-15Yrb` (другой документ, тоже только чтение, доступ по ссылке). Решения:
  - В таблице один лист, поэтому `buildSostavGvizUrl()` не передаёт `sheet=` — gviz сам отдаёт единственный лист.
  - Строки двух типов: «Сборка» (итог по марке — вес, количество) и «Деталь» (один элемент состава). Группирую по столбцу «Марка» в `Map`, а не по «Лист» — у некоторых марок (например, К-1) встречаются повторные/корректирующие строки с другим номером «Лист», но той же маркой; все их детали суммарно попадают в один состав, это и нужно пользователю.
  - Грузится лениво при открытии карточки марки — как «Журнал» — и кэшируется в localStorage так же, через общую `loadFromUrl` в `sheet.js`.
  - Размещена на карточке марки между «Весом/Примечаниями» и «Птичниками» — состав такая же статическая характеристика марки, как вес, а не историческая/распределённая информация (в отличие от истории из «Журнала» и раскладки по птичникам).
- **Ссылки на чертежи** (папка Google Диска с PDF марок и деталей): сопоставление файл→марка/деталь сделано один раз заранее (по имени файла: `Лист_N_Наименование_Марка_ШxВ.pdf` для марок, `Дет.N.pdf` для деталей) и сохранено как статические `drawings/assembly_index.json` / `drawings/parts_index.json`, а не как третий источник, который приложение опрашивает в реальном времени. Причина: Google Drive API/`gviz` не отдаёт список файлов папки без авторизации, в отличие от листов Google Таблиц — поэтому «живое» сопоставление на клиенте невозможно без ключей API, которые по условиям задачи использовать нельзя. Если состав чертежей на Диске изменится — индексы нужно пересобрать вручную (перечислить файлы обеих папок, разобрать имена, перезаписать json).
  - Для марок нашлись чертежи у всех 294 из 294 — ссылка показывается всегда.
  - Для деталей нашлись чертежи у 273 из 338 встречающихся номеров — у остальных деталей в «Составе марки» ссылка просто не отображается (не ошибка, не пустая иконка — кнопки нет совсем).
  - Права на папку и файлы — «Все, у кого есть ссылка: читатель» (проверено явно через Drive API), как и у таблиц, поэтому ссылки открываются без входа в чужой Google-аккаунт.
