# Решения, принятые без подтверждения

Коротко — что решил сам и почему, раз задача требовала работать автономно (см. CLAUDE.md).

- **Статус марки, если ячейка «Статус» пуста**: отгружено ≥ заказа → «Отгружено»; иначе готово ≥ заказа → «Готово»; иначе готово > 0 → «Готово частично»; иначе покрашено > 0 → «Покраска»; иначе изготовлено > 0 → «Изготовление»; иначе «Не начато». Формула подобрана и проверена по реальным строкам снимка (`Б-6`, `Б-10`, `МП-1`, `ПР1-9` и др.) — во всех случаях совпала с готовым статусом из таблицы.
- **Число вида `"1,968"` (запятая без точки)**: если все группы после первой запятой ровно по 3 цифры — это тысячи (`1968`), иначе запятая — десятичный разделитель (`12,5` → `12.5`). Правило из PROMPT.md было неполным для этого случая, выбрал вариант, который даёт верные эталонные суммы.
- **Наименование группы при равной частоте первых слов** (пример из PROMPT.md: «Колонна / Стойка» для группы СТ): беру все слова с максимальной частотой, сортирую по алфавиту и соединяю через « / ». Если слово одно — показываю его одно, без слэша.
- **Сортировка «Марки»**: «по готовности» — по возрастанию (сначала наименее готовые, это то, что обычно нужно увидеть в первую очередь в цехе); «по весу» — по убыванию (сначала самые тяжёлые). В PROMPT.md направление не указано.
- **Экран птичника по умолчанию**: переключатель «Только недостающие / Все» открывается в режиме «Только недостающие» — это чаще нужная информация на складе.
- **Статус птичника «Собирается»**: отдельного цвета в палитре PROMPT.md для него нет, использовал синий (`--status-partial`), как у статуса марки «Готово частично» — тот же смысл «в процессе».
- **Иконка приложения**: логотипа компании не было, сделал простой домик (ассоциация с «птичником») в фирменном синем цвете интерфейса; сгенерирован PNG вручную через Node (`zlib` + ручная упаковка PNG-чанков), без внешних библиотек и сети.
- **Journal (История) недоступна офлайн без кэша**: не считаю это фатальной ошибкой всего приложения — карточка марки открывается, просто блок истории показывает «История недоступна», т.к. основная функция (готовность) не зависит от журнала.
- **Pull-to-refresh**: порог срабатывания — свайп вниз на 90px от верха списка, без отдельного визуального индикатора (используется тот же крутящийся значок «Обновить» в шапке, что и при нажатии кнопки).

## Правки после первой сдачи

- **Баг «не работают прогресс-бары» на «Птичниках» и в карточке марки**: `.bar-fill` — это `<span>` (строчный элемент), а CSS `width`/`height` на обычном строчном элементе браузер игнорирует вообще, даже если значения заданы инлайново. Поэтому заливка полосок была невидимой — виден был только пустой трек. На «Марках» бары работали, потому что там другая реализация (`.stack-bar > span` с `position: absolute`, что блочит элемент автоматически). Исправлено добавлением `display: block` в `.house-stage-row .bar-fill` и `.stage-detail-row .bar-fill` (styles.css).
- **«Состав марки»**: добавлен как отдельный, третий источник данных — Google-таблица `1N9trmeZmpaDhrSThcVps2aFEKQ-15Yrb` (другой документ, тоже только чтение, доступ по ссылке). Решения:
  - В таблице один лист, поэтому `buildSostavGvizUrl()` не передаёт `sheet=` — gviz сам отдаёт единственный лист.
  - Строки двух типов: «Сборка» (итог по марке — вес, количество) и «Деталь» (один элемент состава). Группирую по столбцу «Марка» в `Map`, а не по «Лист» — у некоторых марок (например, К-1) встречаются повторные/корректирующие строки с другим номером «Лист», но той же маркой; все их детали суммарно попадают в один состав, это и нужно пользователю.
  - Грузится лениво при открытии карточки марки — как «Журнал» — и кэшируется в localStorage так же, через общую `loadFromUrl` в `sheet.js`.
  - Размещена на карточке марки между «Весом/Примечаниями» и «Птичниками» — состав такая же статическая характеристика марки, как вес, а не историческая/распределённая информация (в отличие от истории из «Журнала» и раскладки по птичникам).
- **Ссылки на чертежи** (папка Google Диска с PDF марок и деталей): сопоставление файл→марка/деталь сделано один раз заранее (по имени файла: `Лист_N_Наименование_Марка_ШxВ.pdf` для марок, `Дет.N.pdf` для деталей) и сохранено как статические `drawings/assembly_index.json` / `drawings/parts_index.json`, а не как третий источник, который приложение опрашивает в реальном времени. Причина: Google Drive API/`gviz` не отдаёт список файлов папки без авторизации, в отличие от листов Google Таблиц — поэтому «живое» сопоставление на клиенте невозможно без ключей API, которые по условиям задачи использовать нельзя. Если состав чертежей на Диске изменится — индексы нужно пересобрать вручную (перечислить файлы обеих папок, разобрать имена, перезаписать json).
  - Для марок нашлись чертежи у всех 294 из 294 — ссылка показывается всегда.
  - Для деталей нашлись чертежи у 273 из 338 встречающихся номеров — у остальных деталей в «Составе марки» ссылка просто не отображается (не ошибка, не пустая иконка — кнопки нет совсем).
  - Права на папку и файлы — «Все, у кого есть ссылка: читатель» (проверено явно через Drive API), как и у таблиц, поэтому ссылки открываются без входа в чужой Google-аккаунт.
- **Экран «Детали»** (4-я вкладка): номер детали в таблице-спецификации — не уникален на марку, один и тот же физический элемент часто переиспользуется в нескольких марках (пример: деталь №68 — в А1-1, А1-2 и А1-8 одновременно; проверено на снимке — из 338 номеров деталей 167 встречаются больше чем в одной марке). Поэтому сделал отдельный обратный индекс «номер детали → список марок» (`computePartsIndex` в `model.js`, строится на лету из уже загрученного состава, без отдельного запроса к таблице) вместо того, чтобы просто повторять список деталей из карточки марки.
  - Учтены марки, состоящие из одной детали (например Ш1-2) — попадают в индекс наравне с остальными, без особого случая в коде; только поправил грамматику счётчиков («1 деталь» / «2 детали» / «5 деталей», «1 марка» / «2 марки» / «5 марок» — функция `pluralRu` в `app.js`), чтобы с одной деталью/маркой текст не читался коряво.
  - Фильтры (поиск, сортировка «по номеру» / «по числу марок») не сохраняются в localStorage, в отличие от «Марок» — для обратного справочника это не так важно, как для основного списка марок, и это согласуется с тем, что поиск/режим на экране птичника тоже не сохраняются.
- **Баг «не работает фильтрация по статусу» на «Марках»**: сама JS-логика фильтра оказалась исправна (проверено: клик по чипу «Готово» на снимке данных корректно сужает список с 294 до 48 марок). Причина жалобы — `.chip-row` была горизонтально скроллируемой (`overflow-x: auto`): часть чипов пряталась за край экрана, а на сенсорном экране свайп по рядy чипов легко перехватывает тап вместо клика по кнопке — выглядело как «фильтр не работает». Исправлено заменой скролла на перенос строк (`flex-wrap: wrap` вместо `overflow-x: auto`) — все чипы сразу видны и кликабельны без свайпа, как и просили отдельно.
- **«Сколько детали надо на 1 / на N птичников»**: на экране «Детали» добавлено поле «Птичников для расчёта» (своё число, по умолчанию = реальному числу столбцов «Пт N», можно ввести любое — для планирования на будущее расширение, таблицу это не трогает). Потребность детали на 1 птичник = Σ(кол-во детали на 1 экземпляр марки × «На 1 птичник, шт» этой марки) по всем маркам, где деталь встречается (`computePartHouseDemand` в `model.js`) — проверено на детали №68 (в трёх марках с нормами 24/2/2 на птичник → 28 шт/птичник) и на детали №46 из марки-одиночки Ш1-2 (352 шт/птичник, совпадает с уже проверенной раскладкой Пт1 для Ш1-2). Показано и в списке («на 1 птичник», компактно), и на карточке детали (подробно, с тем же полем ввода).
  - Такая же возможность была один раз сделана и для марок (там цифра «На 1 птичник» и так лежит прямо в таблице, считать не нужно), но по просьбе отменена до коммита — на марках её сейчас нет.
- **«Что значат числа на чипах статусов»**: раньше считались по всем 294 маркам всегда, даже если выбрана группа в фильтре — поэтому при выборе группы ФС и клике «Отгружено» список оказывался пуст без объяснения (у ФС действительно 0 отгруженных, но чип этого не показывал). Теперь числа на чипах считаются по уже применённым группе/поиску (но не по статусу — иначе выбранный чип всегда показывал бы сам себя как весь список), так сразу видно, сколько марок текущей группы в каждом статусе.
- **В карточке марки в списке «Марки» добавлена строка с остальными этапами** («Изг · Покр · Гот · Отгр», все четыре числа) — раньше явным текстом было только «Заказано», а изготовлено/покрашено/готово/отгружено угадывались только по цвету слоистой полоски, без цифр.
- **Чипы статусов на «Сводке» и «Марках» теперь считают фактическую активность по этапу, а не финальную метку «Статус»**: на живой таблице обнаружилось, что столбец «Статус» фиксирует ОДНУ финальную метку на марку — например, марка с частичной отгрузкой, но ещё не готовая полностью, помечена «Готово частично», а не «Отгружено», и отгрузка там «теряется». Чип «Отгружено» по старой логике находил только полностью отгруженные марки (48 вместо реальных 151 с хоть какой-то отгрузкой). Добавил `matchesStageActivity`/`computeStageActivityCounts` в `model.js`: каждый чип теперь проверяет соответствующее числовое поле напрямую (made/painted/ready/shipped > 0, «Готово» — ready ≥ заказано), поэтому одна марка может одновременно подходить под «Изготовление», «Покраска» и «Отгружено» — чипы больше не взаимоисключающие, как и фактический прогресс по этапам.
  - На замороженном снимке (`gotovnost_2026-10-18.csv`, где отгрузок ещё не было) новые числа совпадают со старыми — никакая из уже проверенных эталонных цифр не меняется, `computeOverallStats`/`statusCounts` (используется для сверки с «Сводкой» таблицы) не трогал.
  - Бейдж статуса на самой карточке/строке марки — по-прежнему показывает исходный текст из столбца «Статус» как есть, без изменений: он отражает официальную классификацию из таблицы, просто чипы-фильтры теперь дают более полную картину «что вообще происходило с этой маркой».
- **Группы на «Сводке»: добавлено количество по этапам** (Изг/Покр/Гот/Отгр, в штуках) под строкой «N марок · шт · т» — раньше справа была только одна цифра «% изготовлено по весу», без разбивки по остальным этапам. Данные уже были посчитаны в `computeGroups` (через `computeOverallStats` на марках группы), оставалось только вывести `g.stageQty` — новых расчётов не потребовалось.
